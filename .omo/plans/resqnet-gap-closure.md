# resqnet-gap-closure - Work Plan

## TL;DR (For humans)

**What you'll get:** Closure of the six remaining gaps after Phase 1 merged, on their software-executable side. The plan installs onnxruntime + deploys the 3 pre-trained ONNX models from the HuggingFace `resqnet` org and validates inference end-to-end; acquires public real flood/damage datasets (Sen1Floods11, xBD) and wires them into the conformal calibrator for regional calibration; generates a Mumbai PMTiles basemap and enables Redpanda/Redis/Ollama for full offline operation with `GET /api/capabilities` all-green; reruns the complete Docker demo + Playwright e2e + creates the missing Gate E and F1-F4 evidence and reconciles `FINAL_REPORT.md` with reality; adds locust load tests vs 6 concrete SLOs, soak + chaos failure-injection tests, backup/restore scripts, and a secrets-hardening audit; fixes the frontend code-splitting (no chunk >500KB gzip) and the flaky ULID monotonicity test (move `ulid()` before the first `await`); and produces a `SensorSource` protocol + real-device ingestion adapter seam so a physical rescue ball can plug in when built. Three specification documents — a hardware procurement/deployment spec, a physical test-plan, and a field-trial protocol — are delivered as docs only.

**Why this approach:** Three of the six gaps (physical rescue-ball hardware, real sensor procurement/calibration, multi-agency field-trial execution) are fundamentally not software a code-executing worker can perform. Per your decision D1, the plan splits each into (a) software-readiness work a worker CAN execute and (b) an explicit documented deferred milestone, PLUS a hardware specification document and physical test-plan document. The fully-software gaps (offline assets, ML deployment, verification, load/backup/secrets, frontend cleanup) are planned to completion. The Metis gap analysis caught 4 critical issues folded in: capabilities-endpoint gating (onnx/weights are Wave 3, not Wave 2), the PMTiles env-var path mismatch, the model-weights local-vs-MinIO mismatch, and the correct ULID race diagnosis (call-order vs completion-order, not a data race).

**What it will NOT do:** Will NOT build, procure, or manufacture a physical rescue-ball device; will NOT perform physical floodwater/deployment/landing testing; will NOT procure or physically calibrate real sensors; will NOT claim certified human-detection capability; will NOT execute multi-agency field trials; will NOT fabricate model accuracy, weights, benchmarks, or rescue capability; will NOT weaken the graceful-degradation fallbacks (model_unavailable, Redis fail-open, Kafka noop producer, PMTiles vector fallback); will NOT modify merged Phase 1 commits/history; will NOT push to main.

**Effort:** Large — 22 implementation todos across 6 gate-ordered waves + 4 final verification tasks. Each todo is scoped to 1-3 tool calls with exhaustive file references, agent-executable acceptance criteria, happy + failure QA scenarios with evidence paths, and a conventional commit. Wave 1 (frontend cleanup) is independent and quick; Waves 2-3 (offline + ML) are the dependency-heavy core; Waves 4-6 (hardware readiness + spec docs, verification, production validation) build on a working stack.

**Risk:** (1) Docker availability — `FINAL_REPORT.md:435` says Docker was unavailable in the prior environment; T1 verifies it before Wave 2 starts and blocks if missing. (2) HuggingFace `resqnet` model URLs may be dead (the org may be a placeholder) — T7 verifies URLs live before depending on them and marks models `degraded` honestly if dead. (3) Real-dataset acquisition (T9) may be blocked by registration/licensing — fixture-calibration fallback is wired. (4) tippecanoe/Overpass may be unavailable for PMTiles — Geofabrik Mumbai extract fallback specified. (5) The simulator sync-route fix (T14) root cause needs investigation before fixing.

**Decisions:** D1 hardware = software-readiness + spec docs (physical build deferred); D2 ML = deploy pre-trained weights + acquire public datasets for calibration (fixture fallback); D3 SLOs = 50 concurrent / 100 obs/sec / <2s p95 dashboard / <500ms p95 API / 99% over 1h / <30s failover (both profiles); D4 branch = `codex/resqnet-gap-closure`; D5 review = not auto-required (offered at delivery); D6 demo region = Mumbai (the "Rivertown" waypoints at lon 72.85/lat 19.07 are Mumbai coords); D7 test strategy = tests-after, agent-executed QA per todo.
