# Calibrate four SimonK ESCs without guesswork

Upstream SimonK calibration is short. With **valid PWM pulses at or above about 1460 µs already arriving** when the battery is connected, the ESC plays its rising f1 f2 f3 power-up tones and then needs about 0.6 s of steady full-throttle pulses (31 pulses within ±10 µs, at 50 Hz). It confirms with **one beep**. When the input drops to minimum it learns the low point in about 0.7 s and confirms with **two beeps**. It then writes both values to EEPROM and arms at once with a long beep, so **no power cycle is required** ([tgy.asm](https://github.com/sim-/tgy/blob/master/tgy.asm#L2405); [SimonK README](https://github.com/sim-/tgy/blob/master/README.md#throttle-calibration-and-programming)). Driving all four ESCs from the same 1000/2000 µs values at the same moment is valid and is what ArduPilot's "all at once" mode does. Calibration still does not equalise the throttle at which each motor starts spinning, so your ESP32 code needs an idle floor above the slowest motor's start point, as flight controllers use. Your symptoms do not match upstream SimonK. Upstream code plays nothing while you hold full throttle, so **a repeating tune at full throttle means non-upstream firmware**, most likely Hobbywing-style stock firmware that entered its programming menu because full throttle was held too long. If so, your `cal` probably did not store the range you intended. The four-motor failures at 35–40% fit a start-failure or brown-out on a shared power or ground path, not a calibration fault. The recommended fix is a routine that holds full throttle for **3 s** after the battery is connected (staying well inside Hobbywing's roughly 7 s programming-mode limit), then holds minimum for **6 s or more**, then power-cycles. After that, measure each motor's start point and set the idle floor from it.

## SimonK stores max in under a second and arms without a power cycle

In the upstream firmware (sim-/tgy), throttle calibration is compiled in unconditionally (`RC_CALIBRATION = 1`), and no board include file turns it off. The ESC enters calibration whenever it is **disarmed and receives a stable pulse at or above `PROGRAM_RC_PULS`**. That threshold is halfway between the default stop (1060 µs) and full (1860 µs) values, so **1460 µs** ([tgy.asm L189, L219](https://github.com/sim-/tgy/blob/master/tgy.asm#L189)). "Power up at full throttle" is the documented procedure. In the code, though, the check runs on every pulse received while the ESC is waiting to arm. Raising the input above 1460 µs before the ESC has armed has the same effect. The value stored as "high" is simply whatever stable pulse arrives, so calibrating at half throttle would make half throttle the new full.

The high point is accepted after **31 consecutive pulses that each stay within ±10 µs (`MAX_DRIFT_PULS`) of the first**. Any larger deviation makes the routine wait 240 ms and start the count again ([tgy.asm L232, L2404–2449](https://github.com/sim-/tgy/blob/master/tgy.asm#L2404)). Once the high point is stored the ESC plays **one f3 beep**. It then **waits silently with no timeout** for as long as the input stays at or above the learned high. When the input drops, it averages 34 stable pulses, plays **two f3 beeps**, writes EEPROM and returns to the arming loop ([tgy.asm L2457–2474](https://github.com/sim-/tgy/blob/master/tgy.asm#L2457)). Arming needs about 10 consecutive zero-throttle pulses and is announced with **f4 f4 f4 played back to back, which sounds like one long beep** ([tgy.asm L3456–3482](https://github.com/sim-/tgy/blob/master/tgy.asm#L3456)). One user of a HobbyKing 30A SimonK ESC described exactly this pattern: "heard ONE beep, moved the throttle back down … TWO beeps, then ONE LONG beep" ([RCGroups](https://www.rcgroups.com/forums/showthread.php?1961877-SimonK-ESC-no-long-beep-when-calibrating)).

| What you hear (upstream SimonK) | Meaning |
|---|---|
| f1 f2 f3, rising | Clean power-on reset; calibration is allowed |
| f3 f1 ("dead cellphone") | Brown-out reset; **calibration disabled** for this power-up |
| One f3 after the startup tones, then silence | Max pulse captured; waiting for the input to drop |
| Two f3 beeps | Min pulse captured; values written to EEPROM |
| One long f4 (f4 ×3) | Armed |
| f3 roughly every 4–8 s | No valid signal (beacon) |
| f3 f2 | Signal lost while armed; ESC disarms |
| f4 about every 0.5 s while throttle is non-zero | Start failed; repeats until throttle returns to zero |
| Looping f1 f1 f3 f3 | Watchdog reset |

These tones come from the README troubleshooting table and the source ([SimonK README](https://github.com/sim-/tgy/blob/master/README.md#troubleshooting); [tgy.asm L3314–3357, L3842–3854](https://github.com/sim-/tgy/blob/master/tgy.asm#L3314)). Upstream builds hard-code `BLIP_CELL_COUNT = 0`, so **SimonK never beeps out the cell count**. If you hear three short beeps for 3S, the ESC is running different firmware.

The minimum hold times follow from those counts. The power-up tones take about 0.45 s. Capturing max at 50 Hz takes about 0.64 s, and capturing min takes about 0.7 s. In practice **1–2 s at max after power is applied** is enough for SimonK, and holding longer does no harm *on SimonK*. Other firmware is less forgiving. Hobbywing-style ESCs confirm max with "beep-beep" about 2 s after power-up, and **enter programming mode if max is held about 5 s longer** ([Hobbywing Skywalker Quattro manual](https://www.cmldistribution.co.uk/diagrams/HobbyWing/Skywalker%20Quattro%20Manual.pdf)). BLHeli_S needs 3 s above mid-stick and then 3 s below it ([BLHeli_S manual](https://bluerobotics.com/wp-content/uploads/2019/03/BLHeli_S-manual-SiLabs-Rev16.x.pdf)). If you don't know which firmware is installed, **3 s at max followed by 5 s or more at min** works for all three. ArduPilot's automatic routine holds max for 5 s and then holds min until the board is restarted ([ArduPilot esc_calibration.cpp](https://github.com/ArduPilot/ardupilot/blob/master/ArduCopter/esc_calibration.cpp)).

On power cycling, SimonK writes EEPROM by itself and arms immediately, so no power cycle is needed. ArduPilot and Hobbywing-oriented guides still say to unplug and reconnect the battery to leave calibration mode ([ArduPilot](https://ardupilot.org/copter/docs/esc-calibration.html); [Oscar Liang](https://oscarliang.com/how-to-calibrate-esc/)). Your ESCs do not behave like upstream SimonK, so **power-cycle anyway**. It costs nothing. The stored values persist in EEPROM, and there is **no stick command to reset them**. Running calibration again overwrites them ([SimonK README](https://github.com/sim-/tgy/blob/master/README.md#throttle-calibration-and-programming)). SimonK stores deliberately offset values: low is about 17/16 of the measured minimum and high about 31/32 of the measured maximum. A 1000 µs minimum therefore becomes a stop threshold near 1062 µs, which keeps the ESC arming reliably at 1000 µs ([tgy.asm L2412, L2422](https://github.com/sim-/tgy/blob/master/tgy.asm#L2405)).

## Calibration fails silently in six predictable ways

**Brown-out lockout.** The most surprising cause is built into the firmware. Since 2012, SimonK **disables calibration after a brown-out reset**, because the author once accidentally recalibrated an ESC when a weak pack browned out the bus. You hear f3 f1 instead of the rising tones, and the ESC simply arms instead of calibrating. The README says to "cleanly connect the power. If you don't hear the rising beeps, remove the power for a few seconds to allow the capacitors to discharge, then try again" ([SimonK README](https://github.com/sim-/tgy/blob/master/README.md#throttle-calibration-and-programming)). When four ESCs share one XT60, a bouncy plug-in can affect some ESCs and not others, leaving you with **a mix of calibrated and uncalibrated ESCs** and no obvious sign of it.

**Unstable pulses.** Any jitter above ±10 µs restarts the max capture every 240 ms, so the ESC can sit at full throttle without ever beeping. LEDC is not the problem here. A 16-bit LEDC timer at 50 Hz has a 0.31 µs step, and even 12-bit gives 4.9 µs. Ground bounce and marginal logic levels can be a problem, though.

**Pulse not seen at power-up, or below 1460 µs.** If the input is under 1460 µs, calibration is skipped and the ESC goes straight to normal arming ([tgy.asm L2399–2417](https://github.com/sim-/tgy/blob/master/tgy.asm#L2399)). If it is above stop but below 1460 µs, the ESC plays its startup tones and then stays silent and disarmed, which looks like a dead ESC.

**Signal line held high as DC.** Upstream SimonK jumps to its bootloader after about 2 s of continuous high input while disarmed. A floating input can also make the ESC appear to reset when the connector is touched ([SimonK README](https://github.com/sim-/tgy/blob/master/README.md)). A 10 kΩ pull-down on each signal line keeps the input low while the ESP32 boots.

**Thin 3.3 V margin and ground offset.** The ATmega8's V_IH is 0.6 × VCC, which is **3.0 V at 5 V** ([ATmega8A datasheet](https://ww1.microchip.com/downloads/en/DeviceDoc/ATmega8A-Data-Sheet-DS40001974B.pdf)). The ESP32's *guaranteed* V_OH is 0.8 × VDD, which is **2.64 V** ([ESP32 datasheet](https://www.espressif.com/sites/default/files/documentation/esp32_datasheet_en.pdf)). Most units work in practice, but there is no guaranteed margin. Any voltage difference between ESP32 ground and ESC ground comes straight out of the 0.3 V of real-world headroom. A 5 V push-pull buffer (74AHCT125 or SN74ACT244) fixes this properly. Bidirectional MOSFET "I2C" level shifters are a poor substitute ([Arduino forum](https://forum.arduino.cc/t/bldc-motor-not-responding-to-esp32-pwm-via-logic-level-shifter/1402897)).

**Holding max too long on non-SimonK firmware.** On Hobbywing-style firmware, holding max past about 7 s switches the ESC from calibration into the programming menu ([Hobbywing manual](https://www.cmldistribution.co.uk/diagrams/HobbyWing/Skywalker%20Quattro%20Manual.pdf)). One Oscar Liang commenter's ESCs "beep 1, then 2, then 3 times and repeat" when lowered to minimum, which is consistent with landing in a menu ([Oscar Liang comments](https://oscarliang.com/how-to-calibrate-esc/)).

A seventh trap is specific to code. ESP32Servo outputs **1500 µs as soon as `attach()` is called**, which is above SimonK's 1460 µs calibration threshold ([ESP32Servo](https://github.com/madhephaestus/ESP32Servo)). Writing microsecond values directly into `ledcWrite()` without converting them to duty counts produces nonsense pulses ([Arduino forum](https://forum.arduino.cc/t/using-esp32-to-move-brushless-motor-using-esc/1146131)). You use raw LEDC, so the second trap is the one to check.

## One shared signal is valid, but equal start points are not

Calibrating all four together is standard practice. ArduPilot describes its all-at-once mode plainly: "you'll send the same PWM signal to all the ESCs. That's all it does." Hobbywing sells a hub that ties four ESC signal leads to one channel for exactly this purpose ([ArduPilot](https://ardupilot.org/copter/docs/esc-calibration.html); [Hobbywing manual](https://www.cmldistribution.co.uk/diagrams/HobbyWing/Skywalker%20Quattro%20Manual.pdf)). Each SimonK ESC measures the pulse with its own oscillator, and **that per-board measurement is the reason calibration exists**. Boards without an external resonator run on the ATmega8's internal RC oscillator, which "may be off by 5% - 10% between each board, and will also drift by 10% or more over a 40 degree Celsius temperature range" ([SimonK README](https://github.com/sim-/tgy/blob/master/README.md#throttle-calibration-and-programming)). Four separate LEDC channels written with identical values work just as well as one shared pin, as long as **every channel is already outputting max before the battery is connected**. Calibrate on the real 3S pack at room temperature so all four oscillators are in the same state.

Calibration aligns the *pulse-width scale*. It does not align the *motors*. On SimonK, any throttle above the stored low point starts a sensorless start attempt at the minimum duty (about 6.5%). Starting duty is capped at 1/6 and then 1/4 of the power range, but it is **never more than the commanded throttle** ([tgy.asm L235–250, L3586](https://github.com/sim-/tgy/blob/master/tgy.asm#L235)). Near the threshold, bearing friction, the rotor's resting position, prop drag and the oscillator drift left over from calibration decide which motor syncs first. This is why your motors start reliably at about 15% with props on but not at 10%. ArduPilot calls a 1–2% spread between identical ESCs "common" and tells you to "pick the highest percentage of all the motors" ([ArduPilot Setting Motor Range](https://ardupilot.org/copter/docs/set-motor-range.html)). Oscar Liang gives an example quad whose motors started at 1110, 1120, 1130 and 1140 µs, with min throttle set to 1140 ([Oscar Liang](https://oscarliang.com/linear-throttle-response-motor-top-end-calibration/)).

Flight controllers handle this with a measured floor, not with recalibration. ArduPilot sets **`MOT_SPIN_ARM` to the highest per-motor start percentage plus 2%**, and **`MOT_SPIN_MIN` at least 0.03 above that**, so that in flight "we never output a value that causes the motors to stop spinning" ([ArduPilot](https://ardupilot.org/copter/docs/set-motor-range.html)). Betaflight's older PWM-era `min_throttle` was "typically set to just above reliable spin up of all motors", while `min_command` (1000 µs) is what disarmed motors receive ([Betaflight Controls](https://betaflight.com/docs/wiki/guides/current/Controls)). Current Betaflight uses `motor_idle` (default 5.5%) and, with RPM telemetry, a dynamic idle floor based on RPM ([Betaflight CLI](https://betaflight.com/docs/wiki/guides/current/Cli); [Dynamic Idle](https://betaflight.com/docs/wiki/guides/current/Dynamic-Idle)). For your ESP32 this gives three levels:

| Level | Value | Purpose |
|---|---|---|
| Disarmed / stop | 1000 µs | Arming and motors off |
| Armed idle | highest measured start % + 2–3%, about 17–18% with props | Every motor spins; never command anything between stop and this |
| In-flight minimum | idle + 3% or more | Prevents desync and stalls during descent |

Jump straight from 1000 µs to the idle level. Never creep up through the dead band, because startup is the weakest moment for a sensorless ESC.

## A 3 s max, 6 s min routine for Arduino-ESP32 2.0.17

The sequence below combines SimonK's timing with the Hobbywing and BLHeli_S limits and ArduPilot's practice of holding min indefinitely. **Remove the props.** Power the ESP32 from USB first, as both ArduPilot and lobodol's Arduino calibrator do ([ArduPilot](https://ardupilot.org/copter/docs/esc-calibration.html); [lobodol/ESC-calibration](https://github.com/lobodol/ESC-calibration)). Keep the battery disconnected until the code asks for it. **Never start `cal` with the battery connected.** Upstream SimonK would recalibrate if it were still disarmed, but an armed ESC would treat 2000 µs as full throttle and run the motor at full power. Your pins (GPIO 13, 32, 26 and 27) avoid the ESP32 strapping pins 0, 2, 4, 5, 12 and 15 ([ESP32 strapping pins](https://emalliab.wordpress.com/2024/05/20/esp32-strapping-pins/)).

```cpp
// Arduino-ESP32 core 2.0.17 (ledcSetup / ledcAttachPin API)
const int  ESC_PINS[4] = {13, 32, 26, 27};
const uint32_t PWM_HZ = 50, RES_BITS = 16, PERIOD_US = 20000;
const uint32_t US_MIN = 1000, US_MAX = 2000;   // use the SAME values in flight code

uint32_t usToDuty(uint32_t us) { return (us * 65536UL) / PERIOD_US; }  // 1000us -> 3276, 2000us -> 6553
void writeAll(uint32_t us) { for (int ch = 0; ch < 4; ch++) ledcWrite(ch, usToDuty(us)); }

void escInit(uint32_t firstUs) {               // call first thing in setup()
  for (int ch = 0; ch < 4; ch++) { ledcSetup(ch, PWM_HZ, RES_BITS); ledcAttachPin(ESC_PINS[ch], ch); }
  writeAll(firstUs);                           // never let a pin sit idle/high
}

void calibrateEscs() {                         // battery MUST be disconnected when this starts
  writeAll(US_MAX);                            // valid 50 Hz max pulses before ESC power exists
  Serial.println("PROPS OFF. Plug in battery in one clean push, then press ENTER at the startup tones.");
  while (Serial.read() != '\n') delay(5);      // t0 = ESC power-up
  delay(3000);   // SimonK: tones ~0.45 s + 31-pulse capture ~0.65 s -> ONE beep
                 // Hobbywing: "beep-beep" at ~2 s; must leave max before ~7 s; BLHeli_S: 3 s
  writeAll(US_MIN);
  delay(6000);   // SimonK: 34 pulses ~0.7 s -> TWO beeps, then long arm beep
                 // Hobbywing: cell-count beeps + long beep; BLHeli_S: 3 s
  Serial.println("Done. Keep sending 1000 us. Unplug battery, wait 10 s, replug to verify arming.");
  // stay at US_MIN until reset; never stop the pulses or drive the pins DC-high
}
```

Fit a **10 kΩ pull-down from each signal pin to GND** so the inputs stay low while the ESP32 boots. Run a dedicated signal-ground wire from each ESC's servo-lead black wire to a single ESP32 GND point, twisted with its signal wire. Don't daisy-chain the grounds. On a normal (non-calibration) boot, call `escInit(1000)` before anything else and hold 1000 µs for 2–3 s to arm. An ESP32-S3 + SimonK 30A user whose motors would not respond fixed it with exactly that arming hold ([Arduino forum](https://forum.arduino.cc/t/bldc-motor-not-responding-to-esp32-pwm-via-logic-level-shifter/1402897)). Then verify, one motor at a time with props off: step up from 1000 µs in 5 µs increments, record where each motor starts, and check that all four reach full speed at about the same input. Repeat with props on to set the idle floor.

Listen to each ESC during calibration, because the beeps tell you which firmware is installed. **One beep, then two beeps and a long beep** means upstream SimonK. **"Beep-beep", then three short beeps (3S) and a long beep** means Hobbywing-style firmware. **f3 f1 at plug-in** means a brown-out: unplug, wait a few seconds and retry. If all four ESCs beep together, you cannot tell whether one of them did something different. If the results are inconsistent, calibrate each ESC on its own by connecting one ESC's power at a time, which is ArduPilot's fallback method ([ArduPilot](https://ardupilot.org/copter/docs/esc-calibration.html)).

## Your symptoms point to non-upstream firmware and a shared-power fault

**The repeating tune at full throttle.** Upstream SimonK makes no sound in this state. After the single "max captured" beep it waits silently with no timeout. Its only looping sounds are the watchdog siren, the no-signal beacon, the start-failed beacon and an optional noise beep that is off by default, and none of these is a tune played while held at max ([tgy.asm](https://github.com/sim-/tgy/blob/master/tgy.asm#L3314)). The most likely explanation is that these "SimonK 30A" boards run **Hobbywing-style stock or vendor-modified firmware, and your `cal` held max long enough (more than about 7 s after power-up) to enter the programming menu**, which plays its item tones in a loop ([Hobbywing manual](https://www.cmldistribution.co.uk/diagrams/HobbyWing/Skywalker%20Quattro%20Manual.pdf)). This is an inference, because no source documents your exact boards. It has two consequences. First, the throttle range may not have been stored. Second, dropping to min during a menu tone may have **changed a programming setting** (brake, timing or cutoff, for example) instead of calibrating. The beeps 1–2 s after min do not settle the question by themselves. They fit SimonK's two-beep-plus-arm sequence and Hobbywing's cell-count-plus-long-beep sequence equally well. Counting them during the 3 s routine above will tell you which firmware you have. If a menu setting did change, resetting it requires the vendor's procedure or a programming card. Nothing in these notes covers that, so check the seller's manual.

**One motor starting at 12% while the others did not.** This is mostly normal start-threshold spread, made worse by possibly mixed calibration. Your bench already showed starts failing at 10% and succeeding at 15% with props on. A motor that catches at 12% is within the 1–3% spread ArduPilot calls common. If some ESCs kept their old ranges, or reverted to defaults after a brown-out lockout, the spread widens further. Recalibrate cleanly, then set idle to roughly 17–18% as described above. Don't expect calibration alone to bring the four start points together.

**One motor stopping and beeping, another slowing then surging, with all four at 35–40%.** A motor that "stopped and kept beeping" closely matches SimonK's **start-failed state**. The ESC cuts power and beeps f4 about every 0.5 s *until throttle returns to zero*, then disarms ([tgy.asm L3842–3854](https://github.com/sim-/tgy/blob/master/tgy.asm#L3842)). A Hobbywing-style ESC that lost sync behaves in a broadly similar way. Two alternatives can be told apart by the sound. Rising tones mid-run mean the ESC rebooted on low voltage, and it will then sit silent until it sees 1000 µs. f3 f2 means it lost the signal. "Slows then surges" is typical of a desync followed by automatic restart, or a brief ESC reset. Forum experience attributes many such cases to "current draw brownout or vibration induced brownout" ([RCGroups](https://www.rcgroups.com/forums/showthread.php?2920511-What-does-desync-look-like)), and poor wiring shows up "when throttle is increased quickly" ([RCGroups](https://www.rcgroups.com/forums/showthread.php?2718564-What-is-ESC-desync)). The key clue is that **each motor is fine alone**, which points at what the four share. The 3S 5200 mAh 40C pack itself is rated at about 208 A by calculation, far more than four 2212s draw at 40%. The suspects are therefore the battery lead and connector, the power distribution joints, the common signal ground (where shared motor current shifts the ESP32-to-ESC ground and eats into the thin 3.3 V margin), and the bullet connectors on the motor that already snapped a phase wire. Swap the failing motor onto a known-good ESC and GPIO to see whether the fault follows the motor, the ESC or the channel. Wiggle-test the phase bullets. Measure battery voltage at the power distribution point during a four-motor step. Look at one ESC's signal on a scope with all four running. If the code sees a motor commanded on but stopped, have it drop that channel to 1000 µs for 1–2 s so the ESC re-arms.

## Conclusion

The most useful finding is that your ESCs are probably not running upstream SimonK. Everything published about "SimonK calibration" describes code that cannot produce the repeating tune you heard, so treat the firmware as unknown and use timing that is safe for all of them: 3 s at max, 6 s at min, then a power cycle. Count the beeps on that run to identify the firmware. The 35–40% failures are a separate problem that recalibration will not fix. A shared-power or shared-ground fault that only appears under combined current also explains why your earlier 1%/60 ms ramp helped, and it is worth finding on the bench before flight. Once calibration is clean, the remaining step is the one flight controllers always include: measure each motor's start point with props on, and never command a running motor below the highest of them plus a small margin.
